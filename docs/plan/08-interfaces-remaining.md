# 剩余任务 08：接口与文档收尾

基于 `docs/plan/README.md` 问题 18、19，以及问题 4、6、12 的收尾部分。

## 现状

- C API 的点与查询 DTO 已同时保留稠密便捷字段与统一 `vectors` 字段，JSON 侧可表达稀疏、多向量与具名。语言绑定仍只有稠密便捷封装，稀疏与具名只能靠调用方手写 JSON。
- 种类与具名存储的压实已实现并经 `compact_collection` 对外暴露，后台维护线程仍只处理稠密集合的构建与压实调度。种类与具名侧依靠写入阈值触发的快照截断控制日志增长， tombstone 堆积依赖手动压实。
- 内存后端的创建拒绝已明确，但检索侧对非稠密查询的拒绝信息仍间接。具名与种类的生命周期、读写与状态模块仍各自实现精确扫描，评分侧已复用，存储结构因载荷形状不同而保留各自形态。

## 细化方案

- 语言绑定：在现有各绑定内原地补充透传式辅助，不新增传输格式。Python 与 JS 补充具名增量更新、稀疏查询与具名查询的薄封装，内部复用已有的批量写入与查询 JSON 通道。Go、Java 与 R 保持现有通用 JSON 通道不变，文档指引调用方直接使用统一字段，避免为每个语言重复实现距离与校验逻辑。
- 压实调度：本轮不把种类与具名集合接入后台维护线程。后台线程的构建、漂移与 HNSW 修复语义均为稠密专属，强行复用会引入误触发。收尾做法是保持手动压实为正式接口，写入侧的快照截断阈值继续生效，文档中明确手动压实的适用时机。
- 存储复用：种类与具名保留各自的槽表与倒排结构，不做跨模块的统一基类抽取。两者载荷形状不同，统一基类只会增加分支而无检索收益。已复用的评分与截断辅助继续复用，重复的实现保留为各自模块的局部细节。
- 文档同步：README 的向量空间模型段落补充回传完整映射、增量覆盖经 C API 可用、压实为手动接口的说明。能力描述不扩大，不宣称后台自动压实与跨空间 ANN。

## 验收

- Python 与 JS 可经新增辅助完成稀疏写入检索与具名增量更新，无需手写原始 JSON。
- 头文件与 Rust 侧新增入口一致，默认构建不受影响。
- 文档中不再出现与实现矛盾的能力描述。
