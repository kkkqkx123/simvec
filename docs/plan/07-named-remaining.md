# 剩余任务 07：具名向量收尾

基于 `docs/plan/README.md` 问题 9、10、11。

## 现状

- 具名集合已允许每空间独立声明稠密、稀疏与多向量，写入要求一次给齐全量空间，并提供按空间增量覆盖的 `patch` 通道。查询支持单目标与多目标 RRF 融合。
- 单目标检索在要求回传向量时只回传目标空间，调用方无法一次拿到点的完整具名映射。融合检索合并各单目标的回传，而单目标本身不全，导致融合结果的完整性依赖于目标覆盖度。
- 增量覆盖通道只存在于 Rust 引擎层面，C API 与语言绑定均未暴露，外部调用方只能全量覆盖。
- 按空间删除向量未提供。若允许删除单个空间，点将变为部分映射，与写入校验要求的全量映射矛盾，检索侧对缺失空间的期望也会失效。当前全量加增量覆盖已满足增量写入语义，删除语义应收敛为整点删除。

## 细化方案

- 检索回传：在 `src/named_store/read.rs` 的单目标检索中，要求回传向量时回传点的完整空间映射，而非仅目标空间。融合检索保持按目标分别检索再合并分数的流程，因单目标已全量回传，融合结果自然全量。结果类型中的便捷稠密字段保持仅服务单空间稠密路径的语义不变。
- 增量写入暴露：在 `src/c_api/write.rs` 内新增具名增量更新入口，输入为集合名、点标识与空间到载荷的映射 JSON，内部复用引擎已有的增量覆盖方法。同步在 `include/simvec.h` 中补齐声明，保持提交的头文件与 Rust 侧一致。暂不新增按空间删除入口，整点删除仍走删除通道。
- 校验保持：全量写入仍要求空间数量与声明一致，增量覆盖仍逐空间校验类型、维度与多向量上限。未知空间与类型不匹配继续报错，不做部分成功。
- 内存与浏览器形态：继续拒绝具名集合的创建，增量更新入口仅存在于本地引擎与 C API，不向内存后端与浏览器绑定扩散。

## 验收

- 单目标具名检索要求回传时返回完整空间映射，融合检索同样完整。
- C API 可对已有点做单空间增量覆盖，未声明空间与类型错误可预期报错。
- 全量写入缺空间仍失败，增量覆盖不改变未声明空间的已有值。
- 整点删除与按过滤器删除行为不变，不引入部分空间残留状态。
